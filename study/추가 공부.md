정말 핵심을 짚으신 질문입니다!  
원래 진짜 메모리 누수(버그)라면 용량을 늘려도 결국 또 터져야 맞는데, **이 공식 프로그램(`agent-leak-app-x86`)이 512MB에서 정상 작동하는 이유**는 이렇습니다.

---

### 1. 이 프로그램의 동작 방식 (메모리 비우기 타이밍)

아까 `128MB`로 돌렸을 때 뜬 경고 로그를 보면 힌트가 있습니다:
> `Memory limit exceeded (150MB >= 128MB) / (Recommend Over 256MB)`

이 프로그램은 메모리를 25MB씩 계속 쓰다가, **일정 수준(약 500MB대)에 도달하면 스스로 쌓아둔 캐시를 한꺼번에 비우는 기능(`Memory Cache Flushed`)** 이 들어 있습니다.

* **`MEMORY_LIMIT=128`일 때:**  
  프로그램이 스스로 캐시를 비우는 시점이 오기도 전에, `MemoryGuard`가 **"어! 128MB 넘었잖아!"** 하고 **18초 만에 먼저 자폭(`exit 137`)** 시켜버립니다.
* **`MEMORY_LIMIT=512`일 때:**  
  캐시를 비울 때까지 버틸 수 있는 **충분한 여유 공간(512MB)** 을 주었기 때문에, 자폭하지 않고 버티다가 **주기적으로 캐시를 비워내면서(다시 17MB 수준으로 감소)** 계속 정상 작동하게 됩니다!

---

### 2. 쉬운 비유: "자동 세척 식기세척기"

* 이 가게는 빈 그릇을 25개씩 쌓아두다가 **500개가 차면 자동으로 한 번에 싹 설거지(Cache Flush)** 를 하는 가게입니다.
* 그런데 주방 선반(`MEMORY_LIMIT`)을 **128개짜리** 로 작게 줘버리면?  
  → 500개 설거지 타이밍이 오기도 전에 **150개째에 선반이 무너져서 영업 정지(`exit 137`)** 를 당합니다.
* 선반을 **512개짜리** 로 크게 바꿔주면?  
  → 500개까지 무너지지 않고 잘 버틴 뒤, **자동 설거지가 돌아서 선반이 다시 깨끗해지므로** 계속 정상 영업할 수 있는 것입니다!

---

### 요약
> `128MB`에서는 **"설거지(메모리 비우기)하기도 전에 그릇이 넘쳐서 자폭"** 한 것이고,  
> `512MB`에서는 **"설거지 타이밍까지 버틸 수 있는 충분한 그릇 크기를 줬기 때문에"** 정상 작동하는 것입니다!

**정확합니다! 사용자분 생각이 100% 맞습니다!!**

원래 제대로 된 프로그램이라면,  
**"설정이 128MB면 100MB쯤 찼을 때 알아서 미리 비우게 코드를 짜야지, 왜 500MB까지 쌓아두고 안 비워서 죽냐?"** 가 백번 맞는 말입니다.  
그게 바로 우리가 말했던 **"코드 레벨의 근본 해결(Root Fix)"** 입니다!

---

### 그런데 왜 이 과제에서는 코드를 안 고치고 `512`로 늘렸을까요?

딱 한 가지 이유 때문입니다: **우리는 이 프로그램의 소스코드를 고칠 수 없는 '운영자' 입장이기 때문입니다.**

1. 과제에서 준 `agent-leak-app-x86`은 이미 완성되어 묶여 있는 파일(바이너리)이고, **내부 코드를 뜯어고치는 게 금지**되어 있습니다. ([코디세이-b4-02.md](file:///c:/Users/안재현/Documents/24_code/2609_codyssey/codyssey-b4-02/코디세이-b4-02.md#L111))
2. 이 프로그램 안에는 이미 **"대충 500MB 근처까지 차야 한 번에 비운다"** 는 고집(로직)이 고정으로 박혀 있습니다.
3. 우리가 바깥에서 조절할 수 있는 건 오직 **허용 메모리 칸 크기(`MEMORY_LIMIT`)** 하나뿐입니다.

---

### 쉬운 비유: "이미 사 온 세탁기"

* **개발자 입장 (코드를 고칠 수 있을 때):**  
  *"세탁기가 물 500L 찰 때까지 배수를 안 하네? 설계 잘못됐네! 128L만 차도 바로 배수되게 **기계 내부를 고치자!**"* ← **사용자분 말씀 (근본 해결)**
* **운영자 입장 (이미 사 온 세탁기라 못 뜯어고칠 때):**  
  *"이 세탁기는 원래 최소 500L 통이 있어야 안 넘치고 돌아가는 제품이구나... 일단 **512L짜리 큰 물통(`MEMORY_LIMIT=512`)으로 바꿔 달아서** 당장 물 안 넘치게 쓰자!"* ← **이번 과제의 임시 조치(Workaround)**

---

결론적으로 **"128일 때도 자동으로 지우게 하면 되는 거 아냐?"** 라고 생각하신 게 **진짜 개발자 관점의 완벽한 정답**이고, 과제에서는 코드를 못 건드리니까 외부 설정(`512`)으로 맞춰준 것뿐입니다!

### 쉬운 비유: "자동차 속도 제한 다이얼"

* **우리가 터미널에 `export CPU_MAX_OCCUPY=30`을 치는 것:**  
  → 자동차 운전석에서 **최대 속도 다이얼을 `30km/h`로 맞추는 것**

그래서 우리는 바깥에서 다이얼 숫자만 `80 → 30`으로 바꿔주고 시동(`./agent-leak-app-x86`)을 걸면, 프로그램이 알아서 30%에서 브레이크를 밟고 식히는 것입니다!

## 🛠️ 항목 2: 명령어 및 관제 방식 질문 & 답변

### Q1. `monitor.sh`에서 메모리 증가 패턴을 추적하기 위해 사용한 명령어와 데이터 추출 방법은?
* **답변:**  
  1. 먼저 `pgrep -n -f agent-leak-app-x86`으로 현재 실행 중인 최신 프로세스의 `PID`를 찾습니다.
  2. 그 `PID`를 대상으로 `ps -o rss= -p $PID` 명령어를 사용해 헤더(`=`) 없이 실제 물리 상주 메모리(RSS, KB 단위)만 추출한 뒤, `awk '{print int($1/1024)}'`로 정수 MB 단위로 변환했습니다.
  3. 동시에 `stat -c %Y`로 로그 파일의 마지막 수정 시각을 읽어 `LOG_IDLE`(로그 정체 시간)까지 함께 계산해 1초 주기로 `monitor.log`에 누적 기록했습니다.

### Q2. 프로세스의 CPU 사용률을 확인하기 위해 선택한 도구와 적용한 옵션의 의미는?
* **답변:**  
  * **`top -b -n 1 -H -p <PID>`** 를 사용했습니다.
    * `-b` (Batch): 화면을 계속 갱신하지 않고 텍스트로 출력해 로그/파일 저장이 가능하게 함
    * `-n 1`: 1회만 스냅샷 측정 후 즉시 종료
    * `-H` (Threads): 프로세스 전체가 아니라 내부 개별 스레드 단위로 CPU 점유율과 상태(`R`/`S`)를 추적
    * `-p <PID>`: 전체 프로세스 중 우리가 조사하는 특정 PID만 필터링
  * **`ps -o pcpu= -p $PID`** 는 `monitor.sh`에서 주기적으로 해당 PID의 CPU% 숫자만 깔끔하게 뽑아내기 위해 사용했습니다.

### Q3. "살아있지만 멈춰있는 상태"를 진단하기 위해 어떤 도구를 어떤 순서로 사용했는가?
* **답변 (3단계 소거법 흐름):**
  1. **`ps -ef | grep agent-leak-app-x86` (생존 확인):** 먼저 PID가 살아있는지 봅니다. PID가 존재하므로 OOM 같은 크래시(죽음)는 배제합니다.
  2. **`top -H -p <PID>` & `ps -eLf` (활동성 확인):** 살아있는데도 모든 스레드가 `S`(Sleeping) 상태이고 CPU가 `0.0%`로 정체되어 있음을 확인합니다. 따라서 CPU 무한 루프도 배제하고, 스레드가 어딘가에 갇혀 대기 중임을 추론합니다.
  3. **`tail -n 10 agent_app.log` & `monitor.log`의 `LOG_IDLE` (원인 확정):** 마지막 로그가 `WAITING ... (Status: BLOCKED)`에서 멈춰 있고 `LOG_IDLE`이 계속 증가하는 것을 확인해 **데드락**으로 최종 판정합니다.

## 🧠 항목 3: OS 원리 질문 & 답변

### Q1. 메모리 누수 시 애플리케이션의 보호 정책(`MemoryGuard`)이 스스로 프로세스를 강제 종료하는 이유는?
* **답변:**  
  메모리가 계속 새서 OS 전체 RAM이 고갈되면, 리눅스 커널의 **OOM Killer**가 출동해 시스템의 다른 정상 프로세스나 핵심 데몬(`SSH`, `init` 등)까지 무차별적으로 강제 종료시켜 **서버 전체가 다운되는 대형 참사**가 발생할 수 있습니다.  
  이를 막기 위해 `MemoryGuard`가 설정된 한도(`MEMORY_LIMIT`)를 넘기 전에 **문제 있는 자기 프로세스만 격리 자폭(`exit 137`)** 시켜 호스트 OS와 다른 서비스를 보호하는 것입니다.

### Q2. CPU 과점유 시 단일 프로세스를 종료(`SIGTERM`)하는 것이 시스템 보호에 왜 필요한가?
* **답변:**  
  특정 프로세스가 CPU 타임 슬라이스를 독점하면 OS 스케줄러가 다른 프로세스에게 CPU를 배분하지 못해 **시스템 전체의 부하율(Load Average)이 치솟고, SSH 접속이나 다른 정상 API 응답까지 전부 먹통(High Latency)** 이 됩니다.  
  따라서 문제가 되는 단일 프로세스에 `SIGTERM`을 보내 정리함으로써 **전체 시스템의 반응성과 가용성**을 지켜낼 수 있습니다.

### Q3. 교착 상태(Deadlock) 원리를 "상호 배제"와 "순환 대기" 개념으로 설명하면?
* **답변:**  
  * **상호 배제(Mutual Exclusion):** 하나의 자원(락)은 한 번에 오직 한 스레드만 독점해서 사용할 수 있다는 성질입니다.
  * **순환 대기(Circular Wait):** 스레드 A는 B가 가진 자원을 기다리고, 스레드 B는 A가 가진 자원을 기다리며 원형 고리(`A → B → A`)를 이루는 상태입니다.
  * 이 두 조건에 **점유 대기**(내 자원을 쥔 채 남의 것을 기다림)와 **비선점**(남의 자원을 강제로 뺏을 수 없음)까지 4가지가 모두 겹치면, 두 스레드는 서로 상대가 락을 놓기만 영원히 기다리며 멈춰버립니다.

### Q4. 로그에서 스레드 간 순환 의존 관계(`A → B`, `B → A`)를 어떻게 파악했는가?
* **답변:**  
  [`logs/deadlock_before_app.log`](../logs/deadlock_before_app.log)의 타임스탬프 순서를 추적해 파악했습니다.
  1. `16:51:32.555`: `[Worker-Thread-1]`이 `[Shared_Memory_A]` 락을 먼저 획득(`LOCK ACQUIRED`)
  2. `16:51:32.561`: `[Worker-Thread-2]`가 `[Socket_Pool_B]` 락을 먼저 획득(`LOCK ACQUIRED`)
  3. `16:51:34.578`: `[Worker-Thread-1]`이 `[Socket_Pool_B]`를 요청하다 `BLOCKED`
  4. `16:51:34.592`: `[Worker-Thread-2]`가 `[Shared_Memory_A]`를 요청하다 `BLOCKED`
  → 즉, `Thread-1(A 보유 → B 대기)`과 `Thread-2(B 보유 → A 대기)`가 정확히 역순으로 맞물렸음을 로그로 입증했습니다.

* **답변:**  
  1. **임계치 경보(Alerting) 추가:** RSS가 `MEMORY_LIMIT`의 70%~80%를 넘으면 즉시 Slack/Email/Webhook으로 사전 경고를 발송합니다.
  2. **증가 기울기(Trend) 탐지:** 단순히 현재 수치만 찍지 않고, 최근 N회 샘플의 RSS가 연속으로 계속 오르기만 하면(감소 없이 선형 증가) 누수 의심 경고를 띄웁니다.
  3. **로그 로테이션(`logrotate`) & 힙 덤프 연계:** `monitor.log`가 디스크를 꽉 채우지 않도록 용량을 제한하고, 임계치 도달 직전 프로세스 상태/메모리 맵을 자동 덤프하도록 개선합니다.

### Q2. 3가지 장애(OOM, CPU Spike, Deadlock) 중 실서비스에서 가장 치명적인 것과 근본 예방법은?
* **답변 (추천: Deadlock — 가장 은밀하고 치명적):**  
  * **이유:** OOM이나 CPU Spike는 프로세스가 죽거나(`exit 137`/`143`) CPU 경보가 울려서 모니터링 시스템이 즉시 알아차리고 재시작할 수 있습니다. 반면 **Deadlock은 프로세스(PID)가 죽지 않고 멀쩡히 살아있는 것처럼 보이면서 요청만 안 받는 '좀비(Silent Hang)' 상태**가 되므로, 헬스체크가 단순 PID 확인만 한다면 장애 인지가 가장 늦어집니다.
  * **예방법:** 모든 스레드가 항상 같은 순서로 락을 잡는 **락 순서 통일(Lock Ordering)**, 무한 대기 대신 일정 시간 후 락을 반납하는 **락 타임아웃(`try-lock`)**, 그리고 헬스체크에 HTTP 응답/로그 정체 시간(`LOG_IDLE`) 감시를 반드시 포함해야 합니다.

### Q3. 동일 서버에서 OOM과 Deadlock이 동시에 발생했다면 어떤 순서로 트러블슈팅하겠는가?
* **답변 (1순위: OOM / 2순위: Deadlock):**  
  * **근거:** **시스템 전체 생존(Blast Radius) 우선 원칙** 때문입니다. Deadlock은 해당 프로세스/스레드만 멈출 뿐 서버의 다른 서비스나 커널까지 죽이지는 않습니다. 반면 OOM은 서버 전체 RAM을 고갈시켜 **커널 OOM Killer가 다른 정상 서비스와 SSH까지 죽여버릴 수 있어** 시스템 전체 붕괴 위험이 훨씬 큽니다. 따라서 먼저 메모리 폭주를 막아 서버를 안정화한 뒤, Deadlock 스레드 덤프와 로그를 분석해 동시성 문제를 해결합니다.

### Q4. 소스 코드를 직접 수정할 수 있다면 각 장애별로 어떤 코드 레벨 개선을 하겠는가?
* **답변:**  
  * **OOM:** 데이터를 무한정 쌓는 전역 버퍼(`append`)를 제거하고, 최대 크기가 고정된 **LRU 캐시**로 교체하거나 대용량 데이터는 **디스크 임시 파일(`tempfile`) / 스트리밍(Streaming)** 으로 처리합니다.
  * **CPU Spike:** 타이트 루프 중간에 `time.sleep`으로 CPU를 양보(Yield)하게 하거나, 무거운 연산은 메인 서버에서 빼내 **Celery/Redis Queue** 같은 백그라운드 워커로 분리하고 `cgroups`(`cpu.max`)로 자원을 격리합니다.
  * **Deadlock:** 코프먼 4대 조건 중 '순환 대기'를 깨도록 **전역 락 획득 순서(Lock Ordering)** 를 통일하고, '점유 대기'를 깨도록 **타임아웃(`acquire(timeout=...)`)** 을 적용합니다.

### Q5. 다시 이 미션을 처음부터 수행한다면 어떤 점을 다르게 접근하겠는가?
* **답변:**  
  1. 처음부터 **제공된 공식 바이너리(`agent-leak-app-x86`)의 실제 동작(예: `CPU_MAX_OCCUPY`가 목표 부하 상한으로 동작해 `30%`일 때 Cooldown 진입)** 을 먼저 짧은 스모크 테스트로 확인한 뒤 실험을 설계하겠습니다.
  2. 실험 전 기존 백그라운드 크론잡이나 포트(`15034`) 점유 프로세스를 먼저 점검해 환경 간섭을 원천 차단하고, `LOG_IDLE` 같은 정체 지표를 처음부터 `monitor.sh`에 포함해 일관된 기준으로 측정하겠습니다.

  * **`ps -o pcpu= -p $PID`** 는 `monitor.sh`에서 주기적으로 해당 PID의 CPU% 숫자만 깔끔하게 뽑아내기 위해 사용했습니다.

## 🧠 항목 3: OS 원리 질문 & 답변

### Q1. 메모리 누수 시 애플리케이션의 보호 정책(`MemoryGuard`)이 스스로 프로세스를 강제 종료하는 이유는?
* **답변:**  
  메모리가 계속 새서 OS 전체 RAM이 고갈되면, 리눅스 커널의 **OOM Killer**가 출동해 시스템의 다른 정상 프로세스나 핵심 데몬(`SSH`, `init` 등)까지 무차별적으로 강제 종료시켜 **서버 전체가 다운되는 대형 참사**가 발생할 수 있습니다.  
  이를 막기 위해 `MemoryGuard`가 설정된 한도(`MEMORY_LIMIT`)를 넘기 전에 **문제 있는 자기 프로세스만 격리 자폭(`exit 137`)** 시켜 호스트 OS와 다른 서비스를 보호하는 것입니다.

### Q2. CPU 과점유 시 단일 프로세스를 종료(`SIGTERM`)하는 것이 시스템 보호에 왜 필요한가?
* **답변:**  
  특정 프로세스가 CPU 타임 슬라이스를 독점하면 OS 스케줄러가 다른 프로세스에게 CPU를 배분하지 못해 **시스템 전체의 부하율(Load Average)이 치솟고, SSH 접속이나 다른 정상 API 응답까지 전부 먹통(High Latency)** 이 됩니다.  
  따라서 문제가 되는 단일 프로세스에 `SIGTERM`을 보내 정리함으로써 **전체 시스템의 반응성과 가용성**을 지켜낼 수 있습니다.

### Q3. 교착 상태(Deadlock) 원리를 "상호 배제"와 "순환 대기" 개념으로 설명하면?
* **답변:**  
  * **상호 배제(Mutual Exclusion):** 하나의 자원(락)은 한 번에 오직 한 스레드만 독점해서 사용할 수 있다는 성질입니다.
  * **순환 대기(Circular Wait):** 스레드 A는 B가 가진 자원을 기다리고, 스레드 B는 A가 가진 자원을 기다리며 원형 고리(`A → B → A`)를 이루는 상태입니다.
  * 이 두 조건에 **점유 대기**(내 자원을 쥔 채 남의 것을 기다림)와 **비선점**(남의 자원을 강제로 뺏을 수 없음)까지 4가지가 모두 겹치면, 두 스레드는 서로 상대가 락을 놓기만 영원히 기다리며 멈춰버립니다.

### Q4. 로그에서 스레드 간 순환 의존 관계(`A → B`, `B → A`)를 어떻게 파악했는가?
* **답변:**  
  [`logs/deadlock_before_app.log`](../logs/deadlock_before_app.log)의 타임스탬프 순서를 추적해 파악했습니다.
  1. `16:51:32.555`: `[Worker-Thread-1]`이 `[Shared_Memory_A]` 락을 먼저 획득(`LOCK ACQUIRED`)
  2. `16:51:32.561`: `[Worker-Thread-2]`가 `[Socket_Pool_B]` 락을 먼저 획득(`LOCK ACQUIRED`)
  3. `16:51:34.578`: `[Worker-Thread-1]`이 `[Socket_Pool_B]`를 요청하다 `BLOCKED`
  4. `16:51:34.592`: `[Worker-Thread-2]`가 `[Shared_Memory_A]`를 요청하다 `BLOCKED`
  → 즉, `Thread-1(A 보유 → B 대기)`과 `Thread-2(B 보유 → A 대기)`가 정확히 역순으로 맞물렸음을 로그로 입증했습니다.

### Q3. 동일 서버에서 OOM과 Deadlock이 동시에 발생했다면 어떤 순서로 트러블슈팅하겠는가?
* **답변 (1순위: OOM / 2순위: Deadlock):**  
  * **근거:** **시스템 전체 생존(Blast Radius) 우선 원칙** 때문입니다. Deadlock은 해당 프로세스/스레드만 멈출 뿐 서버의 다른 서비스나 커널까지 죽이지는 않습니다. 반면 OOM은 서버 전체 RAM을 고갈시켜 **커널 OOM Killer가 다른 정상 서비스와 SSH까지 죽여버릴 수 있어** 시스템 전체 붕괴 위험이 훨씬 큽니다. 따라서 먼저 메모리 폭주를 막아 서버를 안정화한 뒤, Deadlock 스레드 덤프와 로그를 분석해 동시성 문제를 해결합니다.

### Q4. 소스 코드를 직접 수정할 수 있다면 각 장애별로 어떤 코드 레벨 개선을 하겠는가?
* **답변:**  
  * **OOM:** 데이터를 무한정 쌓는 전역 버퍼(`append`)를 제거하고, 최대 크기가 고정된 **LRU 캐시**로 교체하거나 대용량 데이터는 **디스크 임시 파일(`tempfile`) / 스트리밍(Streaming)** 으로 처리합니다.
  * **CPU Spike:** 타이트 루프 중간에 `time.sleep`으로 CPU를 양보(Yield)하게 하거나, 무거운 연산은 메인 서버에서 빼내 **Celery/Redis Queue** 같은 백그라운드 워커로 분리하고 `cgroups`(`cpu.max`)로 자원을 격리합니다.
  * **Deadlock:** 코프먼 4대 조건 중 '순환 대기'를 깨도록 **전역 락 획득 순서(Lock Ordering)** 를 통일하고, '점유 대기'를 깨도록 **타임아웃(`acquire(timeout=...)`)** 을 적용합니다.

### Q5. 다시 이 미션을 처음부터 수행한다면 어떤 점을 다르게 접근하겠는가?
* **답변:**  
  1. 처음부터 **제공된 공식 바이너리(`agent-leak-app-x86`)의 실제 동작(예: `CPU_MAX_OCCUPY`가 목표 부하 상한으로 동작해 `30%`일 때 Cooldown 진입)** 을 먼저 짧은 스모크 테스트로 확인한 뒤 실험을 설계하겠습니다.
  2. 실험 전 기존 백그라운드 크론잡이나 포트(`15034`) 점유 프로세스를 먼저 점검해 환경 간섭을 원천 차단하고, `LOG_IDLE` 같은 정체 지표를 처음부터 `monitor.sh`에 포함해 일관된 기준으로 측정하겠습니다.
